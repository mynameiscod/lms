Section 1

Executive Summary

The Lead / CRM subsystem is the most feature-complete admin module in the platform — a configurable, multi-tenant pipeline covering intake (website, Meta, Google Ads, Google Sheets, manual/CSV), scoring, distribution, a 21-stage pipeline, follow-ups, qualification, seat-reservation/payment, WhatsApp nurture, AI voice calling, and analytics. It is data-driven: stages, sources, scoring, priority, distribution, forms and qualification are all per-tenant config documents, not hard-coded enums.

Strengths

  • Rich, per-tenant configurable pipeline (21 seeded stages, category-based).
  • Multi-channel intake with a single Lead model + embedded activity log.
  • A real data-visibility layer (leadScope.ts): ALL / TEAM / OWN.
  • Atomic round-robin counters; manager-approval gate on lost stages.
  • Encrypted Meta/WhatsApp creds (AES-256-CBC in LeadSourceConfig).

The 5 things a new engineer must know

  • Two independent auto-assignment paths both write assignedTo on create → last-writer-wins race (leadController.ts:456 & 468).
  • No top-level status: status is derived from stageId → LeadStage.category. Transitions are logged in 3 places that can diverge.
  • Two disconnected conversion paths: seat-reservation creates the Student but never touches the Lead; the lead-side convert targets a "Converted" stage that isn't seeded (silent no-op).
  • Multiple unverified / fail-open webhooks (WhatsApp, Exotel, Meta, Google Ads).
  • Route gates are role-only; fine permissions are enforced for menu visibility, not the routes.
Overall the module is ~72–88% complete depending on sub-area (core CRM 88%, config 85%, distribution/scoring ~75%, WhatsApp automation ~50%, ads ~50%). The gaps are hardening (webhook auth, dedup, conversion wiring, tests) — not missing features.

System Architecture

Transition mechanics (what is actually enforced)

New Lead ──(scoring+assign on create)──► Priority Evaluated / Assigned │ │ ▼ WhatsApp welcome (auto) ▼ calls / follow-ups (manual) Auto WhatsApp Sent ──► WhatsApp Replied Connected ──► Qualified (requiresNote enforced) │ ▼ Follow-up / Meeting / Campus Visit / Demo │ ▼ Payment Link Sent ──► Seat Reserved ──► Enrolled Student (final) │ non-admin → any isLostStage ──► 202 PENDING MANAGER APPROVAL (not applied)
Declared-but-not-enforced: allowedNextStages, allowedPreviousStages, per-stage triggers and sla exist on LeadStage but are not enforced in transition code. Only the hardcoded "Not Interested" reason check and the isLostStage approval gate are live (leadController.ts:648-687).
Conversion no-op: convertToStudent looks up a stage literally named "Converted" (leadController.ts:1243) that is not in DEFAULT_STAGES (the real final stage is "Enrolled Student") — so the stage move silently fails while convertedStudentId is still set.

Section 9

User Journeys (mapped to real scopes)

Roles map to data scopes via leadScope.ts: manage_leads → ALL, assign_leads → TEAM (self + managerId reports), else OWN.

👑 Admin / Owner ALL

Configure stages/sources/scoring/priority/distribution/forms/qualification → monitor all leads & team dashboards → approve lost-stage moves → manage seat reservations & conversions → view analytics/audit. Full CRUD incl. delete + merge.

🧭 Manager / STAFF TEAM

Sees self + direct reports (managerId). Create/edit/assign/convert/export + analytics, but no manage_leads, delete_leads, or manage_lead_stages. Approves? No — lost-stage approval is admin. Works the Manager Board + Team Activity.

📞 Counsellor / Telecaller OWN

Custom role / leadDataScope=OWN: sees only assigned leads → calls, logs activities, schedules follow-ups, answers qualification questions, moves stages (non-lost), sends WhatsApp, requests lost-stage (pending approval).

🎓 Lead → Student (conversion)

Money path: Seat Reservation creates User(STUDENT) + payment via pre-save hook → "enrolled" (never touches the Lead). Lead path: convertToStudent sets convertedStudentId + (broken) stage move. The two are not wired together.

Section 10

Business Rules

Duplicate detection

  • Key = phone last-10-digits only (no email dedup).
  • Create-time 409 block leadController.ts:392-406.
  • Bulk detect/merge (manage_leads) :1768 / :1797.
  • Configurable via LeadFormConfig.settings.duplicateCheckFields / duplicateAction, but no DB unique index backs it.

Validation

  • Create requires only name + phone :373.
  • No email/phone format validation at create.
  • Email validity enforced only at convert :1214-1221.

Scoring (two impls)

  • Create flow: scoreAndAssignLead — sum of matched scoringRule.points; hot/warm thresholds; required-qualification eligibility.
  • Class-based LeadScoringService (priority config, setPriority overrides) — used only by leadPriorityController.

Distribution (dual-path)

  • scoreAndAssignLead = round-robin / rule-based-round-robin over LeadScoringConfig (atomic $inc).
  • autoAssignLead = round-robin / weighted-random over LeadDistributionConfig under a daily cap.
  • Both run on create → race (see §15).
Stage-change rules: Not Interested requires a reason; non-admins moving into an isLostStage get a manager-approval gate (202). All other declared stage constraints are not enforced.

Section 15

Performance Findings (observations only)

  • Double-assignment race — scoreAndAssignLead (awaited) and autoAssignLead (fire-and-forget) both write assignedTo; round-robin counters double-increment; client-returned assignee may not match stored. leadController.ts:456 & 468
  • Distribution daily-cap broken — aggregation compares a String tenantId against ObjectId docs, so the cap never matches. leadDistributionService.ts:57
  • No DB unique index on Lead for the dedup key — dedupe is app-code only; concurrent creates can slip a duplicate through.
  • In-memory rate limiter for public intake (10/min/IP) — lost on restart, not multi-instance-safe. publicLeadController.ts
  • Socket.io single-instance (no Redis adapter) — realtime lead alerts don't survive horizontal scale.
  • 3 parallel transition logs (activities[], LeadStageHistory, AuditLog) — extra writes + drift risk.
  • Large list/board pages fetch broadly; verify pagination + indexes on {tenantId, stageId, assignedTo, createdAt} for scale.
Section 16

Security Findings (observations only)

Unverified / fail-open webhooks: WhatsApp POST has no signature (whatsappWebhookController.ts:211-223); Exotel status webhook has no auth (aiCallWebhookController.ts:29-31); Meta HMAC fails-open + fragile JSON.stringify(req.body) (metaLeadAdsController.ts:222-235); Google Ads fails-open when key unset (googleAdsController.ts:76-84). A forged POST can inject/modify leads & trigger outbound sends.
Weak conversion default: student accounts created from leads use a weak default password Welcome@123. seatReservation / convert flow
Route gating is role-only — fine permissions enforced only for menu visibility; direct-URL access can reach pages the menu hides. 3 authenticated endpoints have no roleGuard; several manage_leads handlers skip the data-scope filter (tenant-only).
Secret fallbacks: encryption key falls back to a hard-coded literal; encrypt() silently stores plaintext on failure; Exotel creds stored plaintext; verify tokens default to literals.

Missing Features

Section 18

Technical Debt

  • Two scoring implementations (create-flow function + class-based service) and two distribution paths — overlapping, one race.
  • Two redundant config models — LeadScoringConfig vs LeadPriorityConfig, each with its own settings page.
  • Dead code: adCampaignController (~490 L, unrouted); adScraperService (Playwright, 699 L, imported by nothing); WhatsApp drip-config endpoints with no UI.
  • Type inconsistency: LeadDistributionConfig.tenantId & WhatsAppConversationState.tenantId are String (no ref) while the rest are ObjectId → the daily-cap bug.
  • Naming mismatch: convert targets stage "Converted"; seeded final is "Enrolled Student".
  • Redundant UI: /lead-kanban duplicates the Board toggle in /leads; activity logging duplicated (Detail + Follow-up modal).
  • No updatedBy, no soft-delete — hard deletes lose history.
Section 19

Improvement Opportunities (observations, not a redesign)

These are neutral observations a future ticket could act on — nothing here has been changed.
  • Consolidate the two assignment paths into one to remove the race and make the returned assignee authoritative.
  • Add a DB unique index for the dedup key to make dedupe race-safe; extend dedup to email.
  • Verify all inbound webhooks (fail-closed) and move verify tokens/secrets out of literal fallbacks.
  • Wire the two conversion paths (seat-reservation ↔ Lead) and fix the "Converted" stage lookup.
  • Pick one scoring + one distribution config; retire the redundant model/page.
  • Make schedulers external / add a Redis Socket.io adapter before horizontal scale.
  • Add tests around scoring, distribution, dedupe, stage transitions, and webhook parsing.
