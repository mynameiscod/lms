What it takes to carry one million members

CareerPilot runs today on a single machine that it shares with two other products. This is an honest reading of where that stops working, in the order it stops working, and what each step up actually costs.

12 Aug 2026 · measured on 187.124.97.56 · slot blue · commit 1b5f0c3b

The short version

Request volume is not your problem. One million members generates roughly 130–400 requests per second at peak, which a single Node process on this hardware can already absorb. Three other things break long before that.

Code execution breaks first — it is throttled to two concurrent heavy runs and shares eight cores with a CRM and a voice product. Durability breaks second — MongoDB is a standalone node with no replica and no backup schedule. Cost breaks third — AI spend is only 1.9% of revenue while quotas are enforced, and unbounded while they are not.

One security item outranks all of it and is not a scale question at all: the JWT signing key is still the framework's published default.

What breaks, in order

Any scale

The JWT signing key is the published default

JWT_SECRET on the production host is still your-secret-key-change-this. Anyone who knows the framework can mint a valid administrator token for your tenant. This is not a capacity problem and it does not wait for growth — it is exploitable today, against 39 members or a million.

Do this firstRotate the secret, force re-login, and rotate the provider keys that were exposed during the two mining incidents. Everything else in this document is optional by comparison.

~2,000 members

Code execution saturates

Heavy languages are limited to two concurrent runs, deliberately, because more than that produced SIGKILLs and drove load from 1.19 to 7.56. Piston shares the same eight cores as the API, MongoDB, a CRM and a voice product — and runs privileged: true, executing arbitrary student code with far more capability than it should have.

FixMove Piston to its own machine. That change alone converts the throttle from a hard product limit into a tuning dial, and takes untrusted code off the host that holds your database.

Any scale

There is no durable copy of the data

MongoDB is a standalone node — no replica, so no failover and no read scaling. The newest backup is five days old and no cron job exists to make another. A restore script previously reported success while restoring zero documents, so the existing archives should be treated as unverified until one is restored and counted.

FixA three-node replica set, a nightly dump with a verified document count, and an off-host copy. Until then, one disk failure ends the business.

~10,000 members

AI cost stops being a rounding error

Measured spend is ₹2.42 per mock interview and ₹30 per member per year — 1.9% of a ₹1,599 membership, which is healthy. That figure assumes the 12-interview cap you specified. No cap is implemented. A member running one interview a day costs ₹883/year, and ten thousand of them would cost more than the module earns.

FixEnforce the quota on the session-start endpoint before the next intake. Half a day of work protecting an unbounded liability.

~50,000 members

One process, one machine, three products

A single Node process serves every request, and the same host runs the CRM and VoicePilot. There is no horizontal scaling and no isolation: a CRM incident takes CareerPilot down with it. Blue/green gives you clean deploys, not availability.

FixSeparate the products onto their own hosts, then put two or more API instances behind the existing nginx. The app is already stateless enough for this — sessions are JWTs and uploads go to disk paths that can move to object storage.

~200,000 members

The frontend is served by the app

A 5 MB JavaScript bundle is served from the application container on every cold visit. At 80,000 daily actives that is bandwidth and CPU the API should not be spending, and every student outside the VPS's region pays the latency.

FixStatic bundle to a CDN. Cheap, unglamorous, and it buys back capacity you would otherwise pay for in servers.

The stale build in version control

The committed client/build/ directory contains a development build with 46 hardcoded localhost:5000 API URLs and REACT_APP_ENV:"development". Nothing ships it today — the Docker image builds the client itself, and the live bundle is clean. But any deploy path that copies that directory instead of rebuilding would push a frontend that points every API call at the student's own machine. Delete it or gitignore it before someone writes that deploy script.

What does not need to change

Several decisions already in the code will hold at a million members, and are worth naming so nobody spends money re-doing them: entitlements are data, not code, so pricing tiers change without a deploy; the coin ledger carries idempotency keys, so retries cannot double-credit; mock-test papers are snapshotted with their answer key and the clock is server-authoritative, so neither a slow device nor a fiddled system clock can buy time; the company readiness bar is computed, never stored, so it can never drift out of sync with the content behind it; and code execution already carries a two-pool queue that distinguishes starvation from an infinite loop. That is a sound foundation. The gaps in this document are operational, not architectural.
