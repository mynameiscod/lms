1 Big picture & actors

The Assignment module is a self-contained vertical: data models, services, REST controllers, and a React UI. Everything is scoped to a tenant (organization) and protected by JWT auth + permission guards.

The three actors

  • Admin / Instructor — authors, publishes, archives, clones assignments; grades submissions; views reports. Needs permissions manage_assignments / grade_submissions.
  • Student — discovers published assignments, attempts them in a workspace, runs code, submits. Needs submit_assignments.
  • System — auto-grades coding/MCQ, runs code via Piston, computes scores & stats, sends email notifications.

2 Data models

Two Mongoose collections drive everything. server/src/models/Assignment.ts and server/src/models/Submission.ts.

Assignment (the template)

  • Identity: tenant, title, description, instructions, type
  • Classification: difficulty, topics[], tags[]
  • Grading: totalPoints, passingPoints
  • Schedule: status, startDate, dueDate, lateSubmissionDeadline, lateSubmissionPenalty
  • Scope: course, subject, chapter, batch
  • Access: accessibleTo (everyone / batch_wise / individual), selectedBatches[], selectedStudents[]
  • Coding: allowedLanguages[], testCases[], starterCode[], timeLimit, memoryLimit
  • MCQ: mcqQuestions[], shuffleQuestions, shuffleOptions
  • Theory/File: rubric[], maxFileSize, allowedFileTypes[], maxFiles
  • Settings: maxAttempts, showTestCaseResults, showExpectedOutput, showSyntaxErrors, enablePlagiarismCheck, enableHints + hints[]
  • Bank: isInBank, bankCategory
  • Cached stats: totals, avg / highest score, avg time

Submission (a student attempt)

  • Keys: tenant, assignment, student, attemptNumber
  • Lifecycle: status = not_started → in_progress → submitted → grading → graded (or late)
  • Timing: startedAt, submittedAt, timeSpent
  • Coding: language, code, codeSnapshots[] (playback), testCaseResults[], compilationError
  • MCQ: mcqAnswers[] (per-question correct + points)
  • Theory/File: theoryAnswer, uploadedFiles[]
  • Scoring: autoScore + manualScore → totalScore − penaltyApplied → finalScore → percentage, isPassing
  • Grading: gradedBy, gradedAt, rubricScores[], overallFeedback, privateFeedback
  • Extras: plagiarismScore, shareToken (LinkedIn), ipAddress, userAgent
Key invariants. A pre-save hook always recomputes totalScore = autoScore + manualScore and finalScore = max(0, totalScore − penaltyApplied). A unique compound index on (tenant, assignment, student, attemptNumber) guarantees one record per attempt. Virtuals expose score (=finalScore) and feedback (=overallFeedback) for the client.

4 Stage 1 — Authoring an assignment

Instructor opens /admin/assignments/create (AdminAssignmentForm.tsx). Every save begins life as DRAFT.

A

Fill the form (or generate with AI / import CSV)

Title, type, difficulty, points, schedule, access, plus type-specific fields (test cases, MCQ questions, rubric…). Three shortcuts exist: AI generation (POST /assignments/generate-ai → OpenAI builds a coding problem + test cases), CSV import (/template/download then /import), and clone an existing one.

client/src/pages/assignments/AdminAssignmentForm.tsx · server aiService.ts

B

POST /assignments → create()

Controller injects tenant + createdBy from the JWT, then assignmentService.create() saves with status: DRAFT. If a chapter was chosen, the assignment id is $addToSet‑linked into that chapter's assignmentIds (curriculum integration).

assignmentController.create → assignmentService.create

C

Edit freely while DRAFT

PUT /:id updates fields; re-pointing the chapter re-links/unlinks automatically. Drafts are invisible to students.

All authoring routes are guarded by roleGuard(['manage_assignments']) and tenantMiddleware, so an instructor can only ever touch their own tenant's data.

5 Stage 2 — Publish & notify

POST /assignments/:id/publish → assignmentService.publish(). This is the gate that makes an assignment real for students.

Validation before publish

  • Title and dueDate are required.
  • coding → at least one allowedLanguage and one testCase.
  • mcq → at least one question.
  • On failure it throws Cannot publish: … and the status stays DRAFT.

On success

  • status → PUBLISHED, updatedBy stamped.
  • Email notifications fire asynchronously (non-blocking) via sendAssignmentNotifications() — the recipient set is resolved from accessibleTo:
    • everyone → all active students in the tenant
    • batch_wise → students whose batchId ∈ selectedBatches
    • individual → students in selectedStudents
    • legacy single batch also supported
Archive instead of delete. DELETE /:id refuses if any submission exists (Cannot delete assignment with existing submissions). Use POST /:id/archive to retire it while keeping history.

6 Stage 3 — Student discovery

GET /assignments/student/list → getStudentAssignments(). Student opens /assignments (StudentAssignmentList.tsx).

  1. Query is hard-filtered to status = PUBLISHED for the current tenant.
  2. The student's batch is resolved (explicit param → else User.batchId).
  3. An $or visibility filter matches: accessibleTo: everyone, OR batch_wise with the batch in selectedBatches, OR individual with the student in selectedStudents, plus legacy records (no accessibleTo) by batch.
  4. For each visible assignment, the student's latest Submission is attached so the UI can show Not started / In progress / Submitted / Score.
  5. Results sorted by dueDate ascending.
This is the access-control heart of the module — a student can never even see an assignment that isn't published and scoped to them.

7 Stage 4 — Attempt & workspace

Student clicks an assignment → /assignments/:id/workspace (AssignmentWorkspace.tsx). The workspace bootstraps an attempt and then loops save/run until submit.

1

POST /:assignmentId/start → startSubmission()

Guards: assignment must be PUBLISHED and past its startDate. Then:

  • If an in-progress submission exists → return it (resume).
  • If a completed one exists and maxAttempts reached → return the last (read-only).
  • Otherwise create a fresh Submission with status=IN_PROGRESS, attemptNumber=1, startedAt=now. For MCQ it pre-seeds blank answers. Duplicate-key races are caught and the existing record returned.
2

Coding loop — auto-save every 30s

The Monaco editor calls POST /submissions/:id/save-code on a 30-second interval. Each save stores code + language and pushes a code snapshot (capped at the last 50) — enabling code-playback later. A countdown timer reflects timeLimit.

3

Run against visible tests

POST /submissions/:id/run → runCode() executes the code against visible test cases only through the code runner. Compilation errors are shown (or masked) per showSyntaxErrors. Results render as pass/fail cards; hidden tests are reserved for final scoring.

MCQ and theory workspaces skip save/run — the student just selects answers / types text and submits.

8 Stage 5 — Submit & auto-grade

Submission is type-specific. Each finalizes the attempt, computes a score where possible, stamps a shareToken, and refreshes cached assignment stats.

Coding — POST /submissions/:id/submit-coding

  1. Runs all test cases (visible + hidden) through the runner.
  2. autoScore = round(earnedWeight / totalWeight × totalPoints).
  3. Hidden test details are stripped from the stored result; expected output only shown if showExpectedOutput.
  4. Late check: if past dueDate → status LATE; within lateSubmissionDeadline a percentage penalty is applied.
  5. finalScore = autoScore − penalty; isPassing = finalScore ≥ passingPoints; status SUBMITTED/LATE.

MCQ — POST /submissions/:id/submit-mcq

  1. Each answer compared to the correct option; pointsEarned accrued per question.
  2. autoScore = round(earned / totalPoints × totalPoints); status set straight to GRADED (fully automatic), with gradedAt stamped.

Theory / File — POST /submissions/:id/submit-theory

  1. Stores theoryAnswer (and uploaded files), sets status SUBMITTED (or LATE). No auto-score — it waits for an instructor.
After coding/MCQ submit, assignmentService.updateStats() recomputes totals, average/highest score and average time, caching them on the Assignment for fast reporting.

9 Stage 6 — Manual grading

For theory / project / file (and any override of auto-scores), the instructor opens /admin/assignments/:id/submissions and grades via POST /assignments/submissions/:submissionId/grade.

  1. Controller accepts either field convention — {score, feedback} or {manualScore, overallFeedback} — and maps client rubric {criterion, score} to server {criterionIndex, pointsAwarded}.
  2. grade() sums rubric points into manualScore, recomputes totalScore = autoScore + manualScore, finalScore, percentage, isPassing.
  3. Stores overallFeedback (visible) + privateFeedback (instructor notes), stamps gradedBy/gradedAt, sets status GRADED, ensures a shareToken, and refreshes stats.
Guard roleGuard(['grade_submissions']). Instructors may view any submission in their tenant; students only their own (enforced in getSubmission).

10 Stage 7 — Reports, sharing & reattempt

Reports (AssignmentReports)

  • /reports/overall — counts by status/type/difficulty, total submissions, avg score.
  • /reports/by-assignment — per-assignment pass rate, on-time vs late.
  • /reports/by-student — per-student completion, avg score, punctuality.
  • /:assignmentId/stats — live grading queue stats (pending, graded, pass rate).

Student result & share

  • Student opens /assignments/:id/result (AssignmentResult.tsx) showing score, test results, feedback.
  • The shareToken powers a public Share-on-LinkedIn certificate link (shareRoutes / shareController).

Reattempt

Instructor calls POST /submissions/:id/allow-reattempt → resets the record to IN_PROGRESS, bumps attemptNumber, clears scores/answers/snapshots so the student can try again.

11 Code execution engine

server/src/services/codeRunnerService.ts abstracts running student code. It has two modes chosen at startup.

ModeWhenHow it works
Real (Piston)PISTON_URL set to a self-hosted instance (not emkc.org)POSTs {language, version, files, stdin} to Piston's /execute. Handles compile errors, runtime errors, signals. For Java the filename is derived from the public class name (else Piston fails). Output compared after normalization (trim, CRLF→LF, strip trailing newlines).
SimulationNo real Piston URL (default/dev)Heuristic engine: bracket-balance + language syntax checks, then pattern-matches common problems (prime, fibonacci, factorial, palindrome, two-sum, binary search, reverse, dedupe…) to synthesize plausible output. Useful for demos without a sandbox.
Note for production correctness: simulation mode only recognizes known patterns — for trustworthy grading a self-hosted Piston must be configured. Languages map to Piston runtimes (JS 18, Python 3.10, Java 15, C/C++ 10.2, etc.).

12 Access control & scoring formulas

Security layers (every request)

  1. authMiddleware — valid JWT.
  2. tenantMiddleware — resolves & injects tenantId; all queries filter by it.
  3. roleGuard([...]) — permission check on admin/grading routes.
  4. Ownership — students restricted to their own submissions.

Scoring math

  • Coding: auto = round(Σ passedWeight / Σ weight × totalPoints)
  • MCQ: auto = round(Σ earned / Σ qPoints × totalPoints)
  • Penalty: round(auto × latePenalty% ) if late but within late deadline
  • Final: max(0, auto + manual − penalty)
  • Pass: finalScore ≥ passingPoints
  • %: round(finalScore / totalPoints × 100)
