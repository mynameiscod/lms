Part A · Understanding the current system

01 Current System Understanding

Source of truth: docs/audit/lead-flow-audit.html + docs/audit/lead-flow/01–06.md. The current CRM is a set of modules inside the CodeBegun LMS monolith (Node/Express + Mongoose/MongoDB, React SPA), multi-tenant via a tenantId field, sharing the LMS auth, users, and deployment.

Scale & shape (traced)

  • 20 Mongoose models (Lead + 19 config/support), 91 HTTP endpoints across 10 areas, 21 seeded pipeline stages, 23 React screens, 5 integrations, 5 in-process schedulers.
  • Auth chain: authMiddleware → tenantMiddleware → roleGuard → leadScope. Data-visibility layer leadScope.ts: manage_leads→ALL, assign_leads→TEAM, else OWN.
  • Integrations: Meta Lead Ads, Google Ads, WhatsApp Cloud, Google Sheets, Exotel (AI voice). Email only for welcome; no SMS.
  • Schedulers are in-process setInterval in server.ts (follow-up 5m, SLA 30m, daily summary 20:00, Sheets sync 5m) + one BullMQ AI-call worker.

Lifecycle reality

  • No top-level status — status is derived from stageId → LeadStage.category (new/engaging/qualified/negotiation/converted/lost).
  • Stage transitions are logged in three parallel places that can diverge: Lead.activities[], LeadStageHistory, AuditLog.
  • Most stage metadata (allowedNextStages, sla, triggers) is declared but never enforced.
  • Dedup key {tenantId, phone(last-10)} is enforced in app code only — no DB unique index.
  • No soft-delete, no updatedBy anywhere; createdBy + timestamps on most models.

Part B · New product architecture

04 New Product Architecture

A modular monolith API + a separate worker process + a Next.js web app, on PostgreSQL/Prisma with Redis/BullMQ. One deployable API, one deployable worker, one web — not 20 services. Internal decoupling comes from domain modules + domain events + transactional outbox, not network boundaries.

crm-web (Next.js) ──REST /api/v1──► crm-api (NestJS modular monolith) ──► PostgreSQL (+ outbox) │ Socket.IO (realtime) │ writes lead + outbox_event in ONE tx │ └──────────────────────────────────────────┤ │ ▼ ▼ crm-worker (NestJS + BullMQ) ◄── outbox dispatcher polls ── Redis (queues) · outbox → domain-event handlers · scheduler (SLA, due/overdue/missed) · automation runner (capability-gated) · analytics projectors · provider adapters (voice/msg/lms…) · webhook processors
Why this shape: the audit's core failures were shared mutable state on one Express process (assignment race, in-process schedulers, 3 activity logs). Splitting API vs worker and routing all side-effects through outbox → events removes the race and the "did it actually run?" ambiguity, without the ops burden of microservices.

07 Module Dependency Rules

Rule 1 — no module imports another module's internals. Modules interact via (a) their public application service, (b) domain events, or (c) shared packages/* contracts. No cross-module Prisma access.
Rule 2 — CRM Core never imports an integration implementation. Core depends on integration-sdk interfaces + the Capability Registry only. leads must never import VoicePilotAdapter.
Rule 3 — dependency direction is one-way. leads/tasks/appointments/conversions → emit events. automation/analytics/activities/integrations → consume. No cycles. Automation calls capabilities, never a module's write API directly except through its public service.
Rule 4 — no tenant-name checks, ever. Behaviour branches only on config, capability presence, or permission — never if (tenant.name === 'CodeBegun').

10 Activity Ledger Design

NEW The single authoritative history. Append-only. Every business/system/provider/migrated event lands here with a verification level, powering both the Lead Timeline and all accountability analytics.

activities id tenant_id entity_type entity_id -- LEAD, TASK, APPOINTMENT… activity_type_id -- CALL_CONNECTED, WHATSAPP_READ… actor_type actor_id -- USER | SYSTEM | INTEGRATION | AI_AGENT verification_type -- SYSTEM_VERIFIED | PROVIDER_VERIFIED -- | MANUAL | MIGRATED source provider -- 'voicepilot','meta','manual' outcome_id? -- e.g. NO_ANSWER occurred_at -- provider timestamp, not insert time metadata JSONB correlation_id causation_id -- trace a chain of events source_system source_record_id -- idempotency for provider/migration created_at UNIQUE(tenant_id, source_system, source_record_id)

Verification is first-class

  • A VoicePilot call → PROVIDER_VERIFIED with real occurred_at, duration, outcome.
  • "Called from my personal phone" note → MANUAL.
  • System-created follow-up-due → SYSTEM_VERIFIED.
  • Imported legacy event → MIGRATED (keeps source_model, migration_batch_id).
  • Managers filter/segment by verification → answers "was it a real integrated call or a manual entry?" (Problem 1).
Solves the audit's 3 divergent logs: Lead.activities[] + LeadStageHistory + AuditLog all collapse into this one ledger; STAGE_CHANGED/OWNER_CHANGED/PRIORITY_CHANGED are ledger entries.

11 Task / Next-Action Engine

REPLACE FollowUpReminder. No lead exists without visibility into Last Activity · Stage · Owner · Outcome · Next Action. Task state is persisted and enforced by a worker — not dependent on browser activity.

tasks id tenant_id lead_id task_type_id title description assigned_to due_at status priority source automation_run_id? outcome_id? created_by completed_by completed_at created_at updated_at status: OPEN|IN_PROGRESS|COMPLETED|MISSED|CANCELLED
Scheduler worker sweeps: OPEN & due_at<now → DUE → OVERDUE → MISSED, emitting task.due/overdue/missed ledger events. This is what makes "13 follow-ups missed" trustworthy (Problem 2).

Next-Action Engine (configurable, not hardcoded)

WHEN stage = QUALIFIED AND outcome = INTERESTED AND no open task of type APPOINTMENT exists THEN CREATE TASK task_type = APPOINTMENT (CodeBegun label: "Demo") due_in = 2h
Rules live in config; CodeBegun labels APPOINTMENT as "Demo". Never hardcode "Book Demo".

15 Reason Taxonomy Engine (objection ≠ lost)

NEW Configurable Category → Reason → Sub-reason, where a reason can be enabled for one or more usage types. Preserves the critical distinction: an objection is not a loss.

The example, preserved

"Fee is high" → occurrence(reason=TOO_EXPENSIVE, usage=OBJECTION, status=OPEN) ... lead still active ... "Joined another institute" → occurrence(reason=JOINED_COMPETITOR, usage=LOST_REASON) → lead.lost.v1 ; final_outcome=LOST ; category=COMPETITOR

Part G · Multi-tenancy, security, permissions

37 Multi-Tenant Design

Shared DB + shared schema; every tenant-owned table has tenant_id (indexed, part of composite keys). Tenant context from AUTH, never from a client-supplied tenantId: Auth → TenantContextGuard (resolves membership) → Application Service → Repository (auto-scopes tenant_id) Defence-in-depth: evaluate Postgres RLS policies on tenant_id. Tenant config/terminology isolated per tenant.
Fixes audit gaps: current system trusts X-Tenant-Id in places and has cross-tenant reachable routes. Here tenant is derived from the authenticated membership; repositories refuse cross-tenant reads/writes.

— Security (webhooks, secrets, passwords)

webhook_events: id tenant_id integration_id provider event_type external_event_id verification_status received_at processed_at status payload JSONB error UNIQUE(integration_id, external_event_id) // idempotent, no replay Every provider that supports signatures → verified, FAIL CLOSED. No unsigned provider webhooks accepted.
  • Integration secrets: application-level encryption at rest; masked to UI; never a hardcoded fallback (fixes current 'secret-key' / plaintext Exotel creds).
  • No weak default passwords (Welcome@123 removed) — conversion/onboarding sets a reset flow.
  • API keys + webhook logs are first-class settings screens.

45 Risks

  • Dual-write during migration — CodeBegun runs on both old (LMS Mongo) and new (Postgres) CRM for a while. Mitigation: one-way legacy→new sync + a cut-over date; new is source of truth post-cutover; freeze old writes.
  • Auth split — bridging LMS JWT to platform identity. Mitigation: adapter first, shared identity later; never duplicate users.
  • VoicePilot boundary — VoicePilot currently is Exotel-era code inside the LMS; extracting it into a callable service with published events is its own effort. Mitigation: adapter can wrap current endpoints initially.
  • Reason sub-taxonomy data loss — old "Not Interested" has no sub-reason; migration can only set the category. Mitigation: mark MEDIUM confidence; capture sub-reason going forward.
  • Demand-gap backfill — old leads never recorded catalog requests; demand analytics is forward-looking unless free-text notes are mined. Mitigation: optional NLP pass over legacy notes (later).
  • Scope — 46 sections is a multi-quarter build. Mitigation: Phases 1–3 deliver a usable CRM; integrations/migration follow.

46 Open Questions (based only on code evidence)

  • "Demo Student" & "Seat Reserved" semantics — are these true conversions (preview enrolment) or negotiation states? Code treats them as [negotiation] stages; the Skill-Assessment funnel also creates preview enrolments. Which is canonical for the new Conversion model?
  • Canonical scoring/distribution config — both LeadScoringConfig and LeadDistributionConfig run on create today. Which one reflects real ops, so the merged engine matches current behaviour?
  • "No Response" = lost or dormant? Code marks it isLostStage, but it's often re-engageable. Should it map to LOST or to a dormant/demand pool?
  • VoicePilot ownership — is VoicePilot a separately deployable Savas service already, or still Exotel logic embedded in the LMS? Determines whether §24 wraps endpoints or consumes real published events.
  • Tenants beyond CodeBegun — is there a confirmed second tenant (e.g. a real-estate client) for launch, or is CodeBegun the sole tenant initially? Affects how much template work ships in Phase 6 vs later.
  • Existing auth source of truth — should platform identity be seeded from the LMS user table, or is a fresh CRM user set acceptable with an SSO bridge? (No code change needed to decide; affects §38 migration.)
  • Payments — current Razorpay lives in the LMS; should the new CRM own payment links/references, or continue delegating to the LMS/other product via a PAYMENT capability?
