Part A · Understanding the current system

01 Current System Understanding

Source of truth: docs/audit/lead-flow-audit.html + docs/audit/lead-flow/01–06.md. The current CRM is a set of modules inside the CodeBegun LMS monolith (Node/Express + Mongoose/MongoDB, React SPA), multi-tenant via a tenantId field, sharing the LMS auth, users, and deployment.

Scale & shape (traced)

  • 20 Mongoose models (Lead + 19 config/support), 91 HTTP endpoints across 10 areas, 21 seeded pipeline stages, 23 React screens, 5 integrations, 5 in-process schedulers.
  • Auth chain: authMiddleware → tenantMiddleware → roleGuard → leadScope. Data-visibility layer leadScope.ts: manage_leads→ALL, assign_leads→TEAM, else OWN.
  • Integrations: Meta Lead Ads, Google Ads, WhatsApp Cloud, Google Sheets, Exotel (AI voice). Email only for welcome; no SMS.
  • Schedulers are in-process setInterval in server.ts (follow-up 5m, SLA 30m, daily summary 20:00, Sheets sync 5m) + one BullMQ AI-call worker.

Lifecycle reality

  • No top-level status — status is derived from stageId → LeadStage.category (new/engaging/qualified/negotiation/converted/lost).
  • Stage transitions are logged in three parallel places that can diverge: Lead.activities[], LeadStageHistory, AuditLog.
  • Most stage metadata (allowedNextStages, sla, triggers) is declared but never enforced.
  • Dedup key {tenantId, phone(last-10)} is enforced in app code only — no DB unique index.
  • No soft-delete, no updatedBy anywhere; createdBy + timestamps on most models.

Part B · New product architecture

04 New Product Architecture

A modular monolith API + a separate worker process + a Next.js web app, on PostgreSQL/Prisma with Redis/BullMQ. One deployable API, one deployable worker, one web — not 20 services. Internal decoupling comes from domain modules + domain events + transactional outbox, not network boundaries.

crm-web (Next.js) ──REST /api/v1──► crm-api (NestJS modular monolith) ──► PostgreSQL (+ outbox) │ Socket.IO (realtime) │ writes lead + outbox_event in ONE tx │ └──────────────────────────────────────────┤ │ ▼ ▼ crm-worker (NestJS + BullMQ) ◄── outbox dispatcher polls ── Redis (queues) · outbox → domain-event handlers · scheduler (SLA, due/overdue/missed) · automation runner (capability-gated) · analytics projectors · provider adapters (voice/msg/lms…) · webhook processors
Why this shape: the audit's core failures were shared mutable state on one Express process (assignment race, in-process schedulers, 3 activity logs). Splitting API vs worker and routing all side-effects through outbox → events removes the race and the "did it actually run?" ambiguity, without the ops burden of microservices.

07 Module Dependency Rules

Rule 1 — no module imports another module's internals. Modules interact via (a) their public application service, (b) domain events, or (c) shared packages/* contracts. No cross-module Prisma access.
Rule 2 — CRM Core never imports an integration implementation. Core depends on integration-sdk interfaces + the Capability Registry only. leads must never import VoicePilotAdapter.
Rule 3 — dependency direction is one-way. leads/tasks/appointments/conversions → emit events. automation/analytics/activities/integrations → consume. No cycles. Automation calls capabilities, never a module's write API directly except through its public service.
Rule 4 — no tenant-name checks, ever. Behaviour branches only on config, capability presence, or permission — never if (tenant.name === 'CodeBegun').
Correction 1 · first-class domain

C1 Lead Ingestion — the ONE door for lead creation NEW

Every source enters through a single ingestion pipeline. Providers (Meta, Google Ads, Website, Generic Webhook, Sheets, CSV/Excel, Manual, WhatsApp, future) only verify + normalize + submit. They must not independently create leads, score, assign, or deduplicate. Manual entry and CSV import also go through this pipeline.

LEAD SOURCE PROVIDER (verify request · normalize payload) ▼ submit lead-ingestion: RAW INTAKE → TENANT RESOLUTION → NORMALIZE → VALIDATE → DEDUPLICATE → RESOLVE SOURCE/CAMPAIGN → CREATE-OR-MERGE ▼ lead.created.v1 OR lead.merged.v1 (via transactional outbox)

lead_intake_records (audit-able intake trail)

id tenant_id provider source_id? external_lead_id? received_at raw_payload JSONB normalized_payload JSONB processing_status lead_id? duplicate_of_lead_id? error_code? error_message? created_at processed_at? UNIQUE(tenant_id, provider, external_lead_id) -- idempotency status: RECEIVED · VALIDATING · VALIDATED · DUPLICATE · CREATED · MERGED · REJECTED · FAILED

Module + rules

  • Module lead-ingestion owns: raw intake, provider normalization, tenant resolution, validation, dedup orchestration (calls the dedup policy), source/campaign attribution, create-vs-merge, ingestion status & error tracking.
  • Async: submissions land on a lead-ingestion queue; the worker processes → writes the intake record + (on success) creates/merges the lead in one tx with the outbox event.
  • Idempotent where a provider external_lead_id exists (unique above); re-delivery updates the same record, never a duplicate lead.
  • Rule: provider webhook controllers do not create leads — they verify → normalize → submit to ingestion (Correction 7).

Required analytics (per provider)

Meta sent 800: Received 800 · Created 742 · Merged 21 Duplicates 22 · Rejected 7 · Failed 8

Monitoring UI — /settings/data/intake

  • Per-provider table: Received · Created · Merged · Duplicates · Rejected · Failed · Last Intake · Last Error.
  • Intake Record detail view for debugging (raw vs normalized payload, status, error, resulting lead/duplicate).
Fixes the audit's "public intake always HOT, no unified normalizer" and the provider-by-provider lead creation — now there is exactly one ingestion path, observable and idempotent.

10 Activity Ledger Design

NEW The single authoritative history. Append-only. Every business/system/provider/migrated event lands here with a verification level, powering both the Lead Timeline and all accountability analytics.

activities id tenant_id entity_type entity_id -- LEAD, TASK, APPOINTMENT… activity_type_id -- CALL_CONNECTED, WHATSAPP_READ… actor_type actor_id -- USER | SYSTEM | INTEGRATION | AI_AGENT verification_type -- SYSTEM_VERIFIED | PROVIDER_VERIFIED -- | MANUAL | MIGRATED source provider -- 'voicepilot','meta','manual' outcome_id? -- e.g. NO_ANSWER occurred_at -- provider timestamp, not insert time metadata JSONB correlation_id causation_id -- trace a chain of events source_system source_record_id -- idempotency for provider/migration created_at UNIQUE(tenant_id, source_system, source_record_id)

Verification is first-class

  • A VoicePilot call → PROVIDER_VERIFIED with real occurred_at, duration, outcome.
  • "Called from my personal phone" note → MANUAL.
  • System-created follow-up-due → SYSTEM_VERIFIED.
  • Imported legacy event → MIGRATED (keeps source_model, migration_batch_id).
  • Managers filter/segment by verification → answers "was it a real integrated call or a manual entry?" (Problem 1).
Collapses the audit's 3 divergent business logs (Lead.activities[] + LeadStageHistory) into this ledger; STAGE_CHANGED/OWNER_CHANGED/PRIORITY_CHANGED are ledger entries. Note the legacy AuditLog does NOT collapse here — see below.

Activity Ledger ≠ Audit Log — two different systems Correction 3

📒 Activity Ledger — business operational truth

  • Lead created/assigned · call started/completed/outcome · WhatsApp replied · task created/completed/missed · stage changed · appointment completed · objection recorded · lead lost · conversion completed · LMS onboarding completed.
  • Powers: Lead 360 Timeline · Employee Activity · operational analytics · Next Best Lead · conversion analysis.

🔒 Audit Log — security / config / admin change history

  • Scoring rule changed · pipeline config updated · reason deleted/deactivated · role permission changed · API key generated · integration credentials updated/disabled · lead email changed A→B · custom-field definition changed · automation rule activated.
  • Powers: security review · compliance · admin investigations · configuration-change tracking.
Both when appropriate. Admin manually changes a lead owner → Activity Ledger: OWNER_CHANGED (actor=USER) and Audit Log: "Lead owner changed from A to B by Admin C". Business events → ledger; administrative/config mutations → audit log; owner-change is both. Module boundaries (§6): activities owns the ledger, audit owns the audit log — they never merge.
Part C · domain engines

11 Task / Next-Action — Status vs Timing State Correction 2

REPLACE FollowUpReminder. Separate a task's persisted STATUS from its derived TIMING STATE. Status is stored and changes via explicit transitions; timing state is computed. The worker is idempotent — it never re-emits task.overdue.v1 on every run.

tasks id tenant_id lead_id task_type_id title description assigned_to due_at grace_minutes? -- from SLA/config status priority source automation_run_id? outcome_id? due_notified_at? overdue_notified_at? missed_at? -- idempotency stamps created_by completed_by completed_at created_at updated_at STATUS (persisted): OPEN | IN_PROGRESS | COMPLETED | MISSED | CANCELLED TIMING_STATE (derived, not stored): status=OPEN & due_at > now → UPCOMING status=OPEN & now ≥ due_at → DUE status=OPEN & now ≥ due_at+grace → OVERDUE status=MISSED (after missed threshold) → (terminal)

Idempotent worker sweep

every tick (BullMQ repeatable): OPEN & DUE & due_notified_at IS NULL → emit task.due.v1 ; set due_notified_at OPEN & OVERDUE & overdue_notified_at IS NULL → emit task.overdue.v1 ; set overdue_notified_at OPEN & now ≥ due_at+missed_threshold → status=MISSED ; set missed_at → emit task.missed.v1 (once)
The *_notified_at stamps guarantee each lifecycle event fires exactly once. Completing an OPEN/DUE/OVERDUE task → task.completed.v1. Timing state is what My Work (§29) and Employee Center (§30) display & count.

Next-Action Engine (configurable, not hardcoded)

WHEN stage = QUALIFIED AND outcome = INTERESTED AND no open task of type APPOINTMENT exists THEN CREATE TASK task_type = APPOINTMENT (CodeBegun label "Demo") due_in = 2h Rules live in config; never hardcode "Book Demo". Implemented via Level-1 Core Rule Execution (§19).

37 Multi-Tenant Design

Shared DB + shared schema; every tenant-owned table has tenant_id (indexed, part of composite keys). Tenant context from AUTH, never from a client-supplied tenantId: Auth → TenantContextGuard (resolves membership) → Application Service → Repository (auto-scopes tenant_id) Defence-in-depth: evaluate Postgres RLS policies on tenant_id. Fixes audit gaps: current system trusts X-Tenant-Id in places and has cross-tenant reachable routes. Here tenant is derived from the authenticated membership; repositories refuse cross-tenant reads/writes.

45 Risks

  • Dual-write during migration — CodeBegun runs on both old (LMS Mongo) and new (Postgres) CRM for a while. Mitigation: one-way legacy→new sync + a cut-over date; new is source of truth post-cutover; freeze old writes.
  • Auth split — bridging LMS JWT to platform identity. Mitigation: adapter first, shared identity later; never duplicate users.
  • VoicePilot boundary — VoicePilot currently is Exotel-era code inside the LMS; extracting it into a callable service with published events is its own effort. Mitigation: adapter can wrap current endpoints initially.
  • Reason sub-taxonomy data loss — old "Not Interested" has no sub-reason; migration can only set the category. Mitigation: mark MEDIUM confidence; capture sub-reason going forward.
  • Demand-gap backfill — old leads never recorded catalog requests; demand analytics is forward-looking unless free-text notes are mined. Mitigation: optional NLP pass over legacy notes (later).
  • Scope — 46 sections is a multi-quarter build. Mitigation: Phases 1–3 deliver a usable CRM; integrations/migration follow.
